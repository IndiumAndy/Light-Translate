## 1. 用户问题与结论

用户反馈：很多页面的翻译不灵敏，时常无法弹出翻译框；具体包括 **Chrome 的部分页面以及顶部导航栏**。

目前确定存在的首要缺陷是：**AX 定位控件时漏做 AppKit → AX 坐标转换**。此外，OCR 限流与悬停只触发一次的组合，会使某次查询被拒绝后一直不再尝试；取词失败只在菜单记录原因，使这些失败表现为“没有反应”。

导航文字的 AX 兼容范围也有限，但具体 Chrome 页面是否受这一点影响，尚需实测。不要把所有失败都归因于同一个原因，也不要仅通过缩短悬停时间处理。

### 证据等级

| 项目 | 当前结论 | 证据与限制 |
|---|---|---|
| 控件命中坐标未转换 | 已确认代码缺陷，优先修复 | 源码调用与 Apple 接口约定不一致；已做合成坐标检查 |
| OCR 限流后静止不补试 | 已确认逻辑组合问题 | 已运行现有 `HoverDwell` 与 `OCRRateLimiter` 的合成时序检查；未运行真实 Chrome 端到端复现 |
| 标签兜底未包含链接/静态文本 | 已确认实现范围有限 | 具体失败网页的 AX role、属性和位置映射能力尚未采集 |
| 取词失败直接关闭浮窗 | 已确认当前行为 | `report(failure:)` 仅保存菜单状态并 dismiss |
| 某个具体页面为何失败 | 待验证 | 用户尚未提供明确网址；本轮没有采集该页面的真实 AX 命中结果 |

## 3. R1：AX 命中控件时漏做坐标转换（最高优先级）

### 位置与依据

- `HoverTranslate/Core/TranslationCoordinator.swift`：默认从 `NSEvent.mouseLocation` 取得指针位置。
- `HoverTranslate/Core/ExtractionSnapshot.swift`：`ExtractionRequest.point` 明确约定为 AppKit 屏幕坐标。
- `HoverTranslate/Extraction/AccessibilityTextExtractor.swift:59`：调用 `AXUIElementCopyElementAtPosition` 时直接传入 `request.point.x/y`。
- 同文件约第 80 行才转换为 `axPoint`，并用于后面的 `AXRangeForPosition`。
- `HoverTranslate/Core/CoordinateMapper.swift` 已有 `appKitToAX`，来源窗口定位与截图流程也已使用它。

Apple 文档明确规定：`AXUIElementCopyElementAtPosition` 接收以屏幕左上为基准的位置。

官方资料：<https://developer.apple.com/documentation/applicationservices/1462077-axuielementcopyelementatposition>

### 影响

同一次取词中，“找控件”与“在控件内找字符”使用了不同坐标。例如主屏高 900 点，AppKit 指针为 `(100, 800)`，应传给 AX 的位置是 `(100, 100)`；当前第一次命中却传 `(100, 800)`，偏差达 700 点。

这可能造成：

- 在其他位置命中空白或无关控件，无法解析鼠标处文字。
- 命中同一应用的错误按钮并返回错误标签；不能只验证“弹出来了”。
- 命中不同应用，PID 校验失败，返回 `unknownOwner`。
- `unknownOwner` 按现有安全策略禁止 OCR，因此即使开启 OCR，也不会补救该次失败。

屏幕顶部通常离上下镜像位置更远，因而与用户提到的顶部区域问题相符；这是机制推断，不是已经完成的页面实测结论。

### 修复方案

1. 在第一次 AX 命中之前取得主显示器参考框，将 `request.point` 转成 AX 坐标。
2. `AXUIElementCopyElementAtPosition` 和后面的 `positionMapping` 使用**同一个转换结果**。
3. 保持 `ExtractionRequest.point` 的 AppKit 坐标约定，避免给其他调用方引入二次转换。
4. 保持返回文字框从 AX 转回 AppKit 的现有约定。
5. 不删除 PID 核对，不将 `unknownOwner` 加入 OCR 可兜底错误集合。

实现方向示意（需结合当前代码整理，不要机械重复声明变量）：

```swift
let primaryFrame = CGDisplayBounds(CGMainDisplayID())
let axPoint = CoordinateMapper.appKitToAX(request.point, primaryFrame: primaryFrame)

let result = AXUIElementCopyElementAtPosition(
    system,
    Float(axPoint.x),
    Float(axPoint.y),
    &element
)
// 后面的 positionMapping 复用 axPoint。
```

### 测试与验收

- 必须覆盖**提取器传给 AX 命中接口的实际位置**，不能只再写一遍 `CoordinateMapper` 的纯函数测试。
- 可增加最小可注入 AX 调用边界，记录测试中收到的命中坐标与字符定位坐标，验证两者一致且只转换一次。
- 覆盖主屏顶部、中部、底部，以及上方/左侧副屏的负坐标；屏幕尺寸由测试注入。
- 验证来源不符仍拒绝，密码控件仍拒绝，失败不绕过到 OCR。
- 真机对同一页面顶部、中部、底部的已知文字验证：浮窗中的原文必须就是指针所指内容。

## 4. R2：OCR 限流被当作终止失败，静止后不会补试（高优先级）

### 位置与依据

- `HoverTranslate/Core/OCRFallbackPolicy.swift`：`OCRRateLimiter.minimumInterval = 0.8`。
- `HoverTranslate/Core/HoverDwell.swift`：停留 0.25 秒后设置 `started = true`，同一锚点不再产生 `.start`。
- `HoverTranslate/Core/TranslationCoordinator.swift`：`allowsOCRFallback` 同时负责策略判断和消耗限流名额，只返回 `Bool`。
- AX 失败且 OCR 未获准启动时直接进入 `report(failure:)`；其中没有安排后续补试，也没有清除悬停的已触发状态。

### 已运行的合成时序检查

使用项目现有类型、合成时间与坐标执行检查，结果符合下列序列：

1. `t = 0`：一次 OCR 获准启动。
2. `t = 0.05`：指针在新的位置建立悬停锚点。
3. `t = 0.35`：新位置达到停留要求，发出一次查询，但 OCR 仍在 800 毫秒间隔内，被拒绝。
4. 指针不动，在 `t = 0.8、1.0、2.0、5.0` 继续采样，`HoverDwell` 均返回 `.none`。

即：等待限流时间过去并不会自动恢复，需要移动超过锚点半径或重新按触发键。该检查验证了现有类型的组合行为；尚未作为协调器完整回归测试落入测试套件。

### 修复方案

1. 区分三类结果：**策略禁止**、**现在可以执行**、**策略允许但需等到指定时间**。不能都压缩成同一个 `false`。
2. 仅对限流等待保留一个待执行请求，并通过现有 ticker 或可注入调度器在最早允许时间补试。
3. 补试前重新验证：触发键仍按住、请求代次有效、模式未变、指针仍在原稳定范围、来源仍一致、当前排除策略及 OCR 权限仍允许。
4. 来源变化或任何核对失败时终止旧请求；不能沿用旧来源窗口盲目截图。
5. 松键、移动超出稳定范围、滚动、普通按键、切换应用、锁屏、禁用功能等均清除待补试任务；固定卡片不能被补试覆盖。
6. 一次悬停最多保留一个等待任务，实际 OCR 不并行启动，不无限循环截图。
7. 不要简单在每次 `report` 后立即 `dwell.reset()`，否则可能形成每隔 250 毫秒重复读取/截图。
8. 暂不把所有失败都自动重试。权限、来源和敏感控件拒绝必须终止；其他瞬态失败的重试需另行证明必要性并设置上限。

### 必须新增的协调器测试

- 两次查询间隔不足 800 毫秒：第二次进入等待，指针静止，到期只补试一次并可显示结果。
- 等待期间松键、移动、切换模式、改变来源或排除策略：旧任务不截图、不显示迟到结果。
- OCR 关闭或未授权：不安排补试。
- 来源不明、密码控件、排除应用：不安排补试。
- 已有 OCR 尚未结束：不得因限流时间到达就重叠执行第二个实际 OCR。
- 补试失败后保持有界，不形成无限循环；未触发时零提取。

测试使用可控时钟和可控完成顺序，不用真实睡眠或真实截图。

## 5. R3：导航文字的 AX 兼容路径有限（需先实测，再针对性补充）

### 已确认的实现情况

`AccessibilityTextExtractor.Limits.standard.labelRoles` 目前仅包含：

- `AXButton`
- `AXCheckBox`
- `AXRadioButton`
- `AXPopUpButton`
- `AXMenuItem`

`boundedLabel` 只读 `title/value`，最长 120 个字符。精确位置映射失败后，链接和静态文本等角色没有标签兜底。

这意味着：若导航文字以链接/静态文本暴露且无法提供精确位置映射，当前 AX 路径可能失败。**不能据此宣称用户所有失败页面都属于这类控件。**

### 先定位“顶部导航栏”具体是什么

实测时分别记录：网页内部导航、Chrome 标签栏/工具栏/书签栏、macOS 系统菜单栏。这些区域可能使用不同 AX 角色和窗口层级，不能混为一种问题。

额外检查点：`PointerWindowPicker` 目前只接受 `layer == 0` 的窗口。非普通窗口层级的菜单/弹出区域可能需要独立归属处理；本轮未证明这是用户当前失败的直接原因，**不要直接移除层级过滤**。

### 修复与诊断方案

1. 先完成 R1，再在实际失败位置采集最小诊断信息：是否收到触发、命中 role、来源是否一致、位置映射返回类别、失败阶段、OCR 是否等待/启动。
2. 日志不得写入正文、译文、URL、窗口标题、路径、截图或密钥。区分“没触发”“AX 失败”“等 OCR”“OCR 无命中”。
3. 对实际确认的短链接/静态标签，考虑增加有边界的兼容路径：来源已确认、敏感控件已排除、命中边界可靠、标签长度受限。
4. 不能仅因为 `AXStaticText` 或 `AXLink` 在新列表里，就无条件读取并翻译整块内容。静态文本也可能是大段正文；大容器仍走有界位置映射或合规 OCR。
5. 如果只能确认整段短标签，应标为 `.label`，不能伪装成鼠标下精确 `.word`。
6. 如需检查邻近父/子元素，必须有明确深度与数量上限，不遍历整页 AX 树，不绕过来源或敏感检查。
7. 不对浏览器辅助功能配置、系统权限或 TCC 数据库做隐式修改。

### 验收

- 短导航链接在已确认支持的页面可以正确显示；无文字的空白区域不能命中旁边的词。
- 大段静态正文不被作为标签整块发送。
- 普通按钮、菜单项、单词、Control 整句模式不回归。
- 记录实际应用版本、页面类型与结果；无法支持的类型清楚标为限制。

## 6. R4：失败静默，让用户误以为没有响应（体验修复）

### 当前行为

`TranslationCoordinator.report(failure:)` 保存 `lastFailure` 后直接 `presenter.dismiss()`。用户必须打开菜单查看 `Last query` 才能看到原因。

另外，原文浮窗在 `show` 中先呈现，然后才发起翻译请求。因此“整个框没出现”应优先排查触发/提取/取消链路，不能直接归咎于 DeepSeek 网络速度；这不排除其他独立网络问题。

### 建议方案

- OCR 正在等限流时，用轻量状态说明“正在识别”，不要当成已失败。
- 最终失败时给出短暂、非激活、不过度打扰的提示，例如“未识别到此处文字”“请先授予辅助功能权限”。文案按项目现有语言风格实现。
- 状态展示要与结果卡区分，不能生成虚假翻译、遮挡正在识别的位置或被自己的 OCR 再次捕获。
- 松键/切换来源后，迟到的状态提示也应受同一代次校验约束，不能重新弹出。
- 对重复空白命中做节流，避免鼠标移动时不断弹错误；固定卡片不被状态提示覆盖。
- 菜单保留失败原因，但避免旧翻译状态遮住最新提取失败。
